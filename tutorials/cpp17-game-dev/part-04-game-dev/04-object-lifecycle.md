# 第四章（下）：对象生命周期与句柄化

适用环境：C++17、CMake 3.16 或更高版本；示例已在 Windows + MSVC 19.50 下验证。

你将学会：

- 解释游戏对象生命周期为什么比普通应用更危险（跨帧引用、加载卸载）。
- 用「索引 + 代数」句柄表管理资源，把悬垂访问变成可检测错误。
- 实现整帧重置的线性帧分配器，掌握 placement new 与显式析构的配对。
- 用 RAII 固化关卡的加载/卸载顺序。

完整代码位于 [生命周期与句柄示例](../code/15-lifecycle-handles/main.cpp)。

## 1. 游戏生命周期的特殊之处

普通应用的对象树跟着调用栈走；游戏世界里对象的生命周期由**事件**驱动：关卡卸载、实体死亡、资源后台加载。由此产生两类经典事故：

1. **跨帧悬垂**：A 系统存了指向 B 实体的裸指针，B 在第三帧死了——之后的每次解引用都是未定义行为，且崩在完全无关的位置。
2. **卸载顺序**：关卡卸载时，先删对象还是先放资源？顺序错了就是「对象析构时解引用已释放的资源」。

第一章 RAII 解决「作用域内」的生命周期；本章处理「作用域外」：引用者与被引用者活在不同的时间尺度上。

## 2. 句柄表：索引 + 代数

`shared_ptr` 能解悬垂，但有两条游戏引擎受不了的成本：控制块原子引用计数（多线程读写热点）与对象头开销。游戏行业的通行解是**句柄表**（handle table）：

```cpp
struct TextureHandle {
    std::uint32_t index;       // 槽位
    std::uint32_t generation;  // 代数
};
```

表内三个平行结构：槽位（`unique_ptr` 数组）、代数数组、空闲槽列表。规则三条：

- **load**：优先复用空闲槽，返回 `(槽位, 当时代数)`；
- **resolve**：代数不符立即返回 `nullptr`——悬垂句柄从 UB 变成可检测错误；
- **unload**：释放槽位、代数加一、槽入空闲表。重复 unload 因 resolve 失败而无害。

示例验证了完整闭环：卸载后旧句柄 resolve 得 `nullptr`；新资源复用同槽位但代数加一；**旧句柄仍然失效**——句柄的安全性质不依赖「地址不重用」，而依赖「代数单调递增」。

```text
hero  = (index 0, gen 0)  →  unload  →  resolve(hero)  == nullptr
slime = (index 0, gen 1)  →  resolve(slime) -> 正常访问
```

句柄是**弱引用**语义：它不阻止资源被卸载，只在访问时验证。需要「引用存在则资源不许销毁」的强语义，才轮到 `shared_ptr`。引擎惯例：跨系统、跨帧传递一律句柄；同帧同作用域内的临时访问才用裸指针。

> ⚠️ 代数递增必须**只在卸载时**发生。句柄的有效性校验依赖「同一占用期内代数不变」；在 resolve 里顺手加一代，所有未过期的句柄会被瞬间误杀。

## 3. 帧分配器：整帧重置的线性 arena

游戏每帧分配大量短命对象（AI 决策缓存、临时向量、字符串拼接结果）。逐个 new/delete 的成本与碎片风险都高。帧分配器把「一帧内所有短命分配」压成一次线性推进：

```cpp
template <typename T, typename... Args>
T* create(Args&&... args) {
    void* aligned = std::align(alignof(T), sizeof(T), start, space);
    // 对齐失败即返回 nullptr：帧内存是预算，不是无限堆
    return new (aligned) T(std::forward<Args>(args)...);  // placement new
}

void reset() { offset_ = 0; }   // 帧末 O(1) 一次性回卷
```

三个要点：

1. **placement new + 显式析构**：`create` 在既有存储上构造（`new (aligned) T(...)`），帧末必须先对每个仍存活的对象显式调 `~T()`（示例的 `destroy`），再回卷 `offset_`——跳过析构就是泄漏非平凡资源。
2. **对齐**：`std::align` 在剩余空间里找对齐地址；`alignof(T)` 决定填充量。
3. **预算语义**：分配失败返回 `nullptr` 而不是抛异常——帧内存是设计预算，超了要改策略（分帧、池扩容），不是等系统兜底。

与第三章任务系统的纪律衔接：**任务内禁止无界分配**，预分配结果缓冲或用帧分配器——worker 抢内存分配器锁是帧内并行最常见的隐性瓶颈。

## 4. 关卡 RAII：加载卸载顺序的固化

关卡加载卸载有严格顺序：先底层资源、后上层对象；卸载按相反顺序（LIFO）。用 RAII 把顺序固化进构造/析构，调用方不可能用错：

```cpp
Level::Level(...) {
    hero_ = table_.load(64, 64);   // 1. 资源
    log_.push_back("objects-spawned"); // 2. 对象
}
Level::~Level() {
    log_.push_back("objects-destroyed"); // 3. 先拆对象引用
    table_.unload(hero_);                // 4. 再放资源
}
```

示例用日志向量逐条断言了四步顺序，并验证边界性质：关卡卸载只释放它加载的资源，外部提前加载的图标（`ui_icon`）完好无损。析构顺序正确时，「对象析构解引用已释放资源」这类事故在结构上不可能发生——这正是第一章「析构函数是唯一可靠清理点」在关卡尺度的应用。

## 5. 三种引用方式的取舍

| 方式 | 强度 | 成本 | 适用 |
|---|---|---|---|
| 裸指针 | 无保护 | 零 | 同帧、同作用域、有明确属主 |
| 句柄 | 弱引用，访问时验证 | 一次代数比较 | 跨帧、跨系统、资源管理 |
| `shared_ptr` | 强引用，阻止销毁 | 原子计数 + 控制块 | 工具链、非热路径的共享所有权 |

决策顺序：能用作用域和属主讲清楚就用裸指针/值；跨生命周期边界就句柄化；确需共享所有权且不在热路径才 `shared_ptr`。引擎里最常见的错误是把第三列用进第一、二列的场景。

## 6. 常见误区

- 裸指针跨帧引用实体/资源：句柄化是默认答案。
- 句柄只存索引不存代数：槽位复用后指向错误对象，且无法检测。
- 帧分配器只回卷不析构：非平凡成员（字符串、容器）的资源全部泄漏。
- 关卡卸载顺序与加载相反之外的自定义顺序：LIFO 是 RAII 的天然保证，偏离要有明确理由并测试。
- 把 `shared_ptr` 用在每帧上万次的实体引用上：原子计数开销直接吃掉帧预算。

## 7. 练习

1. 给句柄表加 `alive(handle)`，并故意在 unload 后再次 unload，验证幂等。
2. 把帧分配器的 `create` 改成超预算时抛异常，再改成返回 `nullptr`，比较两种失败策略在「帧内」语境的可用性。
3. 给 `Level` 增加子关卡列表，验证析构按逆序级联。
4. 写一个「裸指针跨帧悬垂」的最小复现：两个容器交替 clear，指针解引用前用代数校验兜底。
5. 在 ECS（第四章中）上实现「实体句柄校验」版本的世界查询，对比无校验版每帧耗时，量化代数检查成本。

## 8. 小结

- 游戏生命周期的危险来自跨帧引用与事件驱动的销毁。
- 句柄 = 索引 + 代数：弱引用语义，悬垂可检测，卸载幂等。
- 帧分配器：placement new 构造、显式析构、O(1) 回卷；任务是禁止无界分配。
- 关卡用 RAII 固化「资源 → 对象」加载与逆序卸载。
- 引用方式按「裸指针 → 句柄 → shared_ptr」的强度阶梯选择。
